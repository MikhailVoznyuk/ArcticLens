# ArcticLens (Web часть)

## О проекте

**ArcticLens (Web часть)** — демонстрационный веб-контур решения для анализа пространственных данных, подготовленный в рамках хакатонного кейса по выявлению признаков деградации многолетнемерзлых пород на землях сельскохозяйственного назначения.

Проект ориентирован на визуализацию и интерпретацию результатов предварительной GIS- и аналитической обработки данных по двум территориям исследования: **Амга** и **Юнкор**. Веб-приложение предоставляет единый интерфейс для просмотра картографической подложки, аналитических растровых слоёв, контуров объектов, атрибутивной информации по выбранным участкам, а также сводной аналитики в виде карточек и графиков.

## Постановка задачи

В рамках кейса требовалось разработать решение для выявления и визуализации признаков деградации многолетнемерзлых пород на сельскохозяйственных землях. Практическая значимость задачи связана с тем, что деградация мерзлоты в арктических и субарктических районах приводит к развитию термокарстовых процессов, переувлажнению территории, изменению состояния поверхности и, как следствие, к снижению устойчивости использования земель.

Исходная предметная постановка предполагала:

- анализ временного ряда космических данных;
- использование геоинформационных методов для выделения и интерпретации признаков изменений;
- визуальное представление результатов для экспертного анализа;
- поддержку работы с территориально распределёнными объектами в интерактивном интерфейсе.

Настоящий репозиторий содержит именно **веб-часть MVP**, предназначенную для представления и исследования уже подготовленных пространственных слоёв и связанной с ними аналитики.

## Источники данных кейса

Предметный контур решения опирается на следующие типы исходных данных:

- границы территорий работ в формате **ESRI Shapefile** для районов **Амга** и **Юнкор**;
- наборы космических снимков **Канопус-В** за период **2018–2025 гг.**;
- сведения о земельных участках, полученные на основе данных **Публичной кадастровой карты Росреестра**;
- производные GIS- и аналитические слои, сформированные в результате предварительной обработки.

Для целей демонстрации веб-приложение подключается **не напрямую к сырым сценам ДЗЗ**, а к **предварительно подготовленному локальному пакету пространственных данных**. Такой формат выбран осознанно: он обеспечивает воспроизводимую структуру слоёв, стабильную привязку растров, векторов и атрибутивных таблиц, а также позволяет демонстрировать решение локально без зависимости от внешней инфраструктуры и облачных сервисов.

## Назначение веб-приложения

Веб-приложение решает следующие задачи:

- предоставляет интерактивную карту для просмотра территорий исследования;
- позволяет переключать временные срезы и тематические режимы анализа;
- отображает контуры объектов и их атрибутивную информацию;
- поддерживает просмотр аналитических растровых слоёв;
- открывает расширенную аналитику по выбранному объекту;
- сохраняет пользовательский список избранных объектов для повторного просмотра.

Таким образом, приложение выступает как **единый демонстрационный интерфейс** для работы с результатами пространственного анализа и их интерпретации экспертами.

## Функциональные возможности

### 1. Работа с картой

- выбор картографической подложки;
- переключение между территориями **Амга** и **Юнкор**;
- выбор года наблюдения;
- отображение AOI и векторных контуров объектов;
- центрирование карты на выбранной территории или объекте.

### 2. Работа со слоями

Поддерживается отображение нескольких групп слоёв:

- **composites** — базовые годовые композиты;
- **indices** — индексы, включая **NDVI**, **NDWI**, **OSAVI**, Brightness и соотношения спектральных каналов;
- **masks** — бинарные тематические маски;
- **dynamics** — слои межгодовой динамики;
- **terrain** — производные рельефа;
- **experimental** — аналитические производные слои, в том числе `risk_score` и `hotspot_mask`.

В верхнем тулбаре доступны выбор режима карты, года, активного слоя и картографической подложки.

### 3. Работа с объектами

- клик по объекту открывает карточку с основными показателями;
- из карточки можно перейти к расширенной аналитике;
- доступно добавление объекта в список избранного;
- избранные объекты сохраняются в `localStorage` и доступны после перезагрузки страницы.

### 4. Расширенная аналитика

Для выбранного объекта отображаются:

- ключевые метрики по текущему временному срезу;
- временные ряды по доступным годам;
- графики и диаграммы;
- таблица атрибутов текущего года.

## Пользовательские режимы интерфейса

Для упрощения восприятия слоёв реализованы преднастроенные режимы:

- **Базовый режим** — основной сценарий просмотра карты и базовых индексов;
- **Вода** — слои, связанные с водным режимом и переувлажнением;
- **Изменения** — слои межгодовой динамики;
- **Зоны внимания** — производные аналитические слои риска;
- **Рельеф** — terrain-слои;
- **Advanced** — расширенный режим со всеми доступными слоями из пакета.

Такой подход уменьшает перегрузку интерфейса и делает сценарии демонстрации более понятными для пользователя и экспертной аудитории.

## Архитектура решения

Проект состоит из двух частей:

### Frontend

Веб-интерфейс реализован на:

- **Next.js 15**
- **React 19**
- **TypeScript**
- **Tailwind CSS**
- **Leaflet / React-Leaflet**
- **Zustand** для клиентского состояния
- **Recharts** для графиков

Frontend отвечает за:

- отображение карты и UI-элементов;
- загрузку и визуализацию слоёв;
- работу с объектами, popup и модальными окнами;
- управление состоянием пользовательского интерфейса;
- хранение списка избранного на стороне клиента.

### Local backend

Локальный backend реализован на:

- **Fastify**
- **TypeScript**
- **fast-glob** для индексирования набора данных
- **csv-parse** для работы с CSV
- **proj4** для нормализации пространственных данных

Backend отвечает за:

- чтение локального пакета пространственных данных;
- индексирование доступных слоёв и годов;
- отдачу GeoJSON, CSV-агрегатов и путей к растровым слоям;
- разрешение пользовательского запроса «территория + группа слоя + метрика + год» в конкретный файл;
- подготовку данных для карточки объекта и расширенной аналитики.

## Подход к подключению GIS-данных

Для демонстрационного контура используется **предварительно подготовленный локальный data bundle** (`frontend_export`), содержащий согласованный набор векторных, растровых и табличных данных. Такой подход был выбран по следующим причинам:

1. позволяет отделить веб-интерфейс от тяжёлого этапа первичной обработки ДЗЗ;
2. обеспечивает единообразную структуру данных для фронтенда и backend-сервиса;
3. упрощает воспроизводимый локальный запуск в условиях хакатона;
4. снижает требования к инфраструктуре и времени развертывания демо.

С точки зрения интерфейса это означает, что приложение работает с уже подготовленными тематическими слоями и атрибутивными таблицами, а не выполняет первичную обработку космических снимков в рантайме.

## Структура входного пакета данных

Ожидаемая структура каталога с данными:

```text
server/
  data/
    frontend_export/
      manifest.json
      README.txt
      global/
      areas/
        amga/
          analytics/
          vectors/
          rasters/
        yunkor/
          analytics/
          vectors/
          rasters/
```

Backend индексирует:

- `global/*.geojson`
- `areas/<area>/vectors/*.geojson`
- `areas/<area>/analytics/*.csv`
- `areas/<area>/rasters/<group>/*.tif`

## Ключевой поток работы приложения

1. При запуске backend индексирует локальный пакет данных.
2. Frontend получает bootstrap-информацию: территории, годы и доступные группы слоёв.
3. После выбора территории загружаются AOI и контуры объектов.
4. При выборе слоя frontend запрашивает backend для разрешения соответствующего raster-файла.
5. GeoTIFF загружается в интерфейс и отображается поверх карты.
6. При выборе объекта по его `parcel_id` подгружается атрибутивная информация из CSV.
7. Пользователь может открыть расширенную аналитику и сохранить объект в избранное.

## API backend

### `GET /health`
Проверка состояния сервиса.

### `GET /api/bootstrap`
Возвращает:

- список территорий;
- доступные годы;
- набор доступных метрик по группам;
- базовую конфигурацию карты.

### `GET /api/areas/:area/vectors`
Возвращает нормализованные GeoJSON-слои для выбранной территории:

- AOI;
- parcels.

### `GET /api/layers/resolve?area=...&group=...&metricKey=...&year=...`
Разрешает пользовательский запрос к тематическому слою в конкретный файл и возвращает URL для загрузки.

### `GET /api/parcels/:area/:parcelId?year=...`
Возвращает агрегированную информацию по объекту:

- карточку popup;
- метрики для модального окна;
- атрибуты текущего года;
- временной ряд по доступным годам.

## Локальный запуск

### 1. Установка зависимостей

```bash
npm install
```

### 2. Подготовка переменных окружения

Корень проекта:

```env
# .env
# при необходимости может быть пустым
```

Backend:

```env
# server/.env
PORT=4001
GIS_DATA_ROOT=./data/frontend_export
```

Frontend:

```env
# frontend/.env.local
NEXT_PUBLIC_API_BASE_URL=http://localhost:4001
```

### 3. Размещение данных

Распакуйте подготовленный пакет `frontend_export` в каталог:

```text
server/data/frontend_export
```

### 4. Запуск

```bash
npm run dev
```

После запуска доступны:

- frontend: `http://localhost:3000`
- backend: `http://localhost:4001`

## Особенности реализации

- карта работает в клиентском режиме и поддерживает переключение подложек;
- растровые слои подгружаются по запросу, а не загружаются все одновременно;
- контуры объектов и AOI отображаются отдельно от растрового слоя;
- карточка объекта и модальное окно формируются на основе атрибутивных CSV;
- часть дополнительных численных показателей может быть извлечена непосредственно из raster-слоя по координате выбранного объекта;
- избранное хранится в браузере и не требует отдельной серверной базы данных.

## Ограничения текущего MVP

- решение ориентировано на локальную демонстрацию и не включает production-инфраструктуру;
- приложение использует подготовленный data bundle, а не полный вычислительный pipeline обработки космических сцен;
- производительность отображения зависит от размера исходных GeoTIFF-файлов и возможностей браузера;
- для production-эксплуатации целесообразно перейти к COG, tile-based delivery и более формализованному data service слою.

## Возможные направления развития

- подключение tile-based поставки растров;
- отдельный сервис легенд и описаний слоёв;
- поиск по `parcel_id` и другим атрибутам;
- split-screen режим сравнения двух лет;
- экспорт аналитики по выбранному объекту;
- интеграция с расширенным аналитическим или ML-контуром;
- переход от локального демонстрационного хранилища к централизованному опубликованному data service.

## Итог

Разработанный веб-контур решает задачу представления результатов пространственного анализа в удобной интерактивной форме. Проект демонстрирует, каким образом можно связать картографическую подложку, тематические растровые слои, объектную геометрию и атрибутивную аналитику в едином пользовательском интерфейсе для экспертной оценки состояния исследуемых территорий.
